# Slice 26 — Record Status/hold + per-record notification preferences

Two-session slice. Session 1 landed DB + procs + API; session 2 landed tests + web + wiring + docs. The four `Dn` divergences below are the resolved cut-plan questions reviewers need for the DB diff; the additional cut-plan decisions capture smaller runtime choices.

## Divergences resolved at cut-plan time

- **D1 — Hold state currently lives in `FieldValues` JSON, not in `Hold BIT` / `HoldReason` columns.** The v2 addendum described a *before* state that never actually landed — the scaffold implementation used JSON keys `$.holdBlocked` and `$.holdReason`. Resolution (analyst-approved): migration 060 **adds** `StatusHold` + `StatusHoldNote` columns; migration 061 backfills from the JSON keys; the JSON keys are **left in place** and mirrored on every write so the condition engine's Display/Mirror Status derivation (BS §3.4) continues to see consistent values — same pattern `usp_SetRequestStage` uses today for `$.stage`.
- **D2 — Proc names in the addendum don't match the real procs.** Addendum names `usp_CompleteTask` and `usp_DecideApproval`; the real procs are `usp_PatchTask` (task complete = `PATCH` with `Status='Done'`) and `usp_SubmitDecision`. Guards land in the real procs. No code effect — recorded so future readers don't grep for the wrong names.
- **D3 — Guard scope on `usp_PatchTask`.** Blanket-guarding every `usp_PatchTask` call on a held record would also block innocuous edits (notes, typed-field values). Resolution: **guard fires only when `@SetStatus=1 AND @Status='Done'`**. Notes, phases, assignments, and typed-field values remain editable while a record is held. Approvals guard is unconditional (`usp_SubmitDecision` blocks Approve and Reject — the addendum's "pauses gate approvals" is unambiguous). Stage-advance guard is unconditional (`usp_SetRequestStage`).
- **D4 — `WatcherNotificationPreference` table shape.** The v2 addendum's proposed shape includes an `IsWatching` column and keys on `(UserId, RecordId)`, implying the new table *replaces* the existing `dbo.Watchers` presence table. But `Watchers` is per-side `(RecordId, WorkspaceId, UserId)` and carries `SubscribedAt`/`UnsubscribedAt` history the preference shape lacks. Resolution: keep `dbo.Watchers` as the presence source of truth; add `dbo.WatcherNotificationPreference` as a **sparse per-side preference layer** with no `IsWatching` column, keyed on `(UserId, RecordId, WorkspaceId)`. A missing preference row means all five defaults (`true`) apply. `PATCH /records/{id}/watchers/me` splits: `isWatching` still routes through `usp_AddWatcher` / `usp_RemoveWatcher` (via `Watchers`); the five preference booleans route through `usp_UpsertWatcherPreference` (via the new table). Migration 063 (backfill of preferences from watchers) is dropped as unnecessary — a sparse table with defaults-all-true requires no backfill.

## Additional cut-plan decisions

- **`usp_PatchRequest` unchanged.** The tri-state PATCH routes through the new dedicated `usp_UpsertRequestStatusHold`, not through the sparse content patch. The API service (`RequestsService.PatchAsync`) will call the new proc when `statusHold` is present on the request body and route `hold` through the same call after the legacy-shape translation.
- **`usp_SetRequestHold` left in place until API rewires.** Superseded by `usp_UpsertRequestStatusHold`; can be deleted once `RequestsService` and any callers switch to the new proc. Tracked as slice-26 cleanup, not a new decision.
- **SQL THROW number `51201` = `record-on-hold`.** Same code for both `OnHold` and `Abandoned` states — the addendum specifies `Abandoned` maps to the same 409 as `OnHold`. The UI can distinguish via the record's `statusHold` field in the response, not via the error code.

## API contract additions (already landed)

- `RequestDto.statusHold: 'InProgress' | 'OnHold' | 'Abandoned'` (required) + `statusHoldNote: string | null` (optional).
- `RequestListRow.statusHold` — projected on every S2 row so the pill renders without a per-row detail fetch.
- `RequestPatchRequest.statusHold` + `statusHoldNote` accepted; legacy `hold: { held, reason }` accepted for one release and mapped server-side (`held=true → OnHold`, `held=false → InProgress`).
- Legacy binary hold: `POST /requests/{id}/hold` retained but now routes through `usp_UpsertRequestStatusHold`.
- New `PATCH /records/{recordId}/watchers/me` — sparse update of the caller's `isWatching` + five preference booleans. Returns the refreshed `WatcherListDto`.
- New response fields on `WatcherListItemDto` — caller's own row carries `notifyGateDecisions / notifyStatusChanges / notifyTaskSignoffs / notifySlaAndDueDateReminders / notifyMentionsAndComments`. Other rows omit the fields entirely.
- 409 ProblemDetails code `record-on-hold` returned by `PATCH /requests/{id}` (via ROLLBACK if a status change conflicts), `POST /requests/{id}/stage`, `PATCH /tasks/{id}` (Status→Done only, D3), `POST /approval-requests/{id}/decisions`.

## Follow-ups (out of scope for this slice — deliberately deferred)

- **Home API projection of `statusHold`.** The shared Home types now carry an optional `statusHold`; the pill renders on Work / Decisions / Triage cards when the field is present. The API-side projection (extending `usp_GetHome` or the composite Home service) to actually populate the field is a small follow-up that requires a schema-diff + procedure edit. The UI is safe as-is — the pill is a no-op when the field is undefined.
- **`usp_SetRequestHold` cleanup.** Superseded by `usp_UpsertRequestStatusHold` and the legacy `POST /hold` endpoint now translates through the new proc. The old proc can be deleted once no in-flight branch depends on it — tracked as a small dedicated cleanup PR.
- **Optimistic-update polish for the preference toggles.** Every check/uncheck currently sends a PATCH and awaits the round-trip before the next interaction. An `onMutate` optimistic update would make the toggles feel snappier. Non-blocking — the current UX is honest and correct.
