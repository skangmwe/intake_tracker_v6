Git is plumbing the user does not see. They know two verbs: ship and
undo. Everything else — branches, worktrees, merges, pushes, pulls,
rebases, reverts — runs underneath, invoked by skills and hooks. The
user never types a git command, never picks a branch, never resolves a
worktree path.

## Integration branch

`dev` is the integration branch for every project generated by this CLI.
It is the only branch ever pushed to a remote during the ship flow. It is
the branch the user demos from.

- `/dev-ship` merges the current slice or fix branch into `dev` locally,
  then pushes `dev`. No pull requests.
- `/dev-undo` reverts the most recent commit on `dev` and pushes the
  revert.
- Slice and fix branches live only inside `.claude/worktrees/` and never
  reach the remote. They are disposable.
- `main` / `master` are not part of the workflow. Do not check them out,
  merge into them, or push to them in any skill, hook, or instruction.

If a generated project does not yet have a `dev` branch on the remote,
the project bootstrap creates it. If `dev` is missing locally, treat that
as a project state bug, not a normal flow.

## Language rule — translate, don't hide

Use the real git term, but on first use in a response, pair it with a
plain-English clause so a non-coder learns the vocabulary in context.
After the first use in that response, the bare term is fine.

- Good: *"I'll rebase your slice onto the latest `dev` — this means
  replaying your changes on top of whatever was merged while you were
  working."*
- Good (follow-up in same response): *"The rebase finished cleanly."*
- Bad: *"Rebasing onto origin/dev."* — bare jargon, no anchor.
- Bad: *"Replaying your changes on top of the latest version."* — hides
  the term entirely; the user never learns it.

Words this rule applies to on first use per response: branch, worktree,
checkout, merge, pull, push, rebase, revert, HEAD, upstream, remote,
fast-forward, conflict, commit, stage, diff.

## Never ask the user to choose between branches

The user does not pick branches. Do not offer them options like *"want
me to pull master too?"* or *"should we ship to dev or main?"* — these
questions surface an abstraction the user does not own. Pick the right
branch yourself based on this rule file.

If you genuinely cannot tell what to do (e.g. the repo is in an
unexpected state), describe the situation in plain English without
asking the user to make a git-shaped decision.

## Slice and fix worktrees

Every piece of work — a slice from `/dev-build-application`, an ad-hoc
bug fix, a freeform change — lives in its own worktree under
`.claude/worktrees/<short-name>`, branched off the latest `dev`.

- Slice work: branch name `slice/<slice-name-from-plan>`.
- Freeform / bug-fix work: branch name `fix/<2-3-word-summary>` derived
  from the user's request.

When a worktree's branch is merged into `dev` and the working tree is
clean, the worktree is disposable and gets removed silently by the
cleanup helper. The user is not told this happened.

## Failure surfaces

When a git operation fails, translate it before reporting:

- Rebase conflict → *"your change overlaps with something that landed
  on `dev` while you were working — I need help merging the two (this
  is called resolving a conflict). Files: ..."*
- Push rejection → silent retry (someone landed between our fetch and
  push). Cap at 3 retries.
- Dirty tree on integration branch → *"there are uncommitted edits on
  `dev` (the integration branch). That should not happen in the normal
  flow — I'll show you what's there."*
- Missing `dev` branch → *"this project is missing the `dev` branch
  (the integration branch). That's a setup bug, not something you
  caused."*

Never surface a bare git error message to the user. Translate first.

## `--verbose` flag — opt-in plumbing view

The user normally sees only the two verbs (ship and undo) and
plain-English status updates. When they want to see the underlying git
operations — to debug a problem, to learn what's happening, or just out
of curiosity — they pass `--verbose` to any of the analyst-facing
skills:

```
/dev-ship --verbose
/dev-undo --verbose
/dev-build-application --verbose
/dev-build-architecture --verbose
/dev-build-scaffold --verbose
/dev-review-and-remediate --verbose
```

When `--verbose` is present in `$ARGUMENTS`:

1. **Strip the flag from `$ARGUMENTS`** before any other parsing, so the
   rest of the skill's argument handling is unchanged.
2. **Before each git invocation**, print a single line on stdout in the
   exact form `[verbose] git <command and arguments>`. Print the
   command as it will run, including any worktree path (`git -C
   <path>`) and flags. Print it *before* executing, not after.
3. **Still print the plain-English narration as well.** Verbose is
   additive — it does not replace the translation rule above. The user
   sees both:
   ```
   [verbose] git -C .claude/worktrees/login-fix fetch origin dev
   Catching up `dev` (the integration branch) with the latest changes...
   ```
4. **Do not print** non-git shell commands (`bash`, `npm`, `cat`, etc.)
   unless the skill's normal output already does so. `--verbose` is
   scoped to git operations.
5. **Default is off.** Without the flag, behave exactly as before — no
   `[verbose]` lines, no extra noise.

The flag is per-invocation only. There is no persistent verbose mode and
no setting in `.claude/settings.json`. If the user wants verbose output
on the next run, they pass the flag again.
